# Multigent 2.x Agentic 架构演进说明

> 日期：2026-08-26
> 用途：给客户、团队成员和合作方做产品/架构展示，解释最近一轮核心改动为什么要做、为什么面向未来、会带来什么收益，以及如何落地。

## 一句话结论

Multigent 2.x 的核心变化，是把系统从“项目里的 Agent 执行工具”升级为“拥有长期身份、注意力、并发工作能力和共享上下文环境的 Agent 协作组织”。

这不是为了堆概念，而是为了支持更真实的工作方式：

- Agent 不只是被动执行任务，而是像同事一样持续醒来、观察、判断、沟通和推进。
- 流程不再是僵硬自动化脚本，而是人和 Agent 共同遵守的协作规范。
- 外部消息、任务、文档、会议、Issue、PR、客户反馈等，不应该一次性塞进 prompt，而应该进入可治理的上下文与注意力系统。
- 一个长期 Agent 可以同时推进多件工作，但不会膨胀成一堆失控的临时 Agent。

## 背景：旧模型为什么不够

Multigent 早期模型已经能跑通任务、流程、Agent、IM 协作、运行节点和外部工具。但真实客户场景暴露出几个更底层的问题。

### 1. Agent 被项目成员模型限制住了

旧模型里，Agent 更像“项目里的一个成员”。这在单项目任务里是合理的，但当我们希望一个 Agent 像人一样跨多个项目工作时，就会变得别扭：

- 同一个 Agent 需要重复挂到多个项目里。
- Agent 的长期身份、模型配置、协作渠道和工作节奏容易跟项目 membership 混在一起。
- 用户想和某个 Agent 聊长期话题，但系统却容易把它理解成某个项目里的某次任务对话。

真实世界里，人是组织里的长期成员；项目只是人参与工作的上下文。Agent 也应该如此。

### 2. 消息被误解成触发器

IM 单聊、群聊 @、站内消息、任务分配、流程节点变化、GitHub 更新，本质上都是“外部世界里发生了需要 Agent 关注的事”。

如果系统把它们都做成 webhook trigger，就会出现两个问题：

- 每条消息都触发 Agent，成本高、干扰多，也不像真实同事。
- Agent 失去自主性，只是在执行系统写死的 callback。

更合理的是：系统把这些事情记录成 Attention Signal，Agent 在自己的心跳或被唤醒时，根据优先级、上下文和职责判断要不要处理、怎么处理。

### 3. 单会话串行无法支撑真实吞吐

一个开发 Agent 可能同时收到 10 个插件接入任务；一个 QA Agent 可能同时要评审多个 PR；一个 PM Agent 可能要分流一批 Issue。

如果一个 Agent 永远只有一个主会话串行处理，吞吐会很低。但如果系统直接创建 `dev-1`、`dev-2`、`dev-3` 这些长期 Agent，又会造成身份、权限、审计、沟通和管理混乱。

我们需要的是：一个长期 Agent 主体，能够派生可追踪的工作会话并发推进。

### 4. 仅靠 prompt 和 session 记忆不稳定

随着事情变多，Agent 需要知道的信息分散在：

- Lark / Feishu 群聊和私聊。
- 飞书文档、会议纪要。
- GitHub Issue / PR / Review / CI。
- Linear / Sentry / 用户反馈。
- 本地 Agent session、历史交接文档、截图、文件。
- 竞品动态、文章、推文、行业信息。

这些内容不能都塞进 system prompt，也不能只留在某个 Agent 的原生 session 里。我们需要一个可抓取、可沉淀、可检索、可授权、可遗忘的上下文中心。

## 新模型：四个核心改动

### 1. Agent Worker 从项目中独立出来

新的模型把 Agent 拆成两个层次：

```text
Agent Worker = 这个 Agent 是谁
Project Membership = 这个 Agent 在某个项目中以什么身份工作
Task / Workflow = 这个 Agent 在某个项目里推进哪件具体工作
```

Agent Worker 拥有长期身份：

- 名称、头像、标识。
- 团队和角色。
- 模型账号和运行配置。
- 长期行为准则 / system prompt。
- 心跳唤醒策略。
- IM 协作渠道。
- 外部工具和权限。
- 主会话和工作会话。

项目 membership 只表达它在项目中的职责：

- 在 `tapnow-mcp-server` 项目里，Mason 是 MCP Server 开发者。
- 在 `tapnow-agent-platform` 项目里，Nova 是项目管理者。
- 同一个 Agent 可以加入多个项目，但仍然是同一个长期主体。

收益：

- 用户可以在一级“智能体”页面管理所有 Agent。
- Agent 的长期身份不会被项目切碎。
- 项目仍然提供任务、流程、文档、权限和上下文边界。
- 后续支持“一个 Agent 跨多个项目工作”会更自然。

### 2. Attention Signal 初步搭建

Attention Signal 的作用不是触发器，而是 Agent 的“注意力队列”。

它表达：

- 谁找了我。
- 哪个群聊 @了我。
- 哪个任务需要我处理。
- 哪个流程节点轮到我了。
- 哪个外部系统有我可能需要关注的变化。
- 用户点击了我发出的卡片。

它不应该承载大量正文。Signal 只保存摘要、来源、优先级、时间、可信身份和 `context_ref`。

Agent 在 wakeup 时看到这些信号后，可以自主决定：

- 马上处理。
- 先查更多上下文。
- 回复人类确认。
- 忽略。
- 转给其他 Agent。
- 创建任务或推进流程。

关键机制：

- `seen`：表示这条 signal 已经被展示给 Agent，不再重复塞进去。
- `handling / handled / ignored`：表示业务处理状态。
- 防抖：短时间内多个 IM 消息合并唤醒，避免一次群聊产生十几个 run。
- 心跳策略：是否因为私聊、@、卡片点击、任务分配提前唤醒，由 Agent 的心跳配置决定。
- 审计：记录信号来自谁、Agent 做了什么、是否代表某个用户操作。

收益：

- 外部世界的信息可以统一进入 Agent 的注意力模型。
- 不同来源的事件不会变成一堆散乱的 webhook handler。
- Agent 更像同事：它可以选择关注、延后、询问或主动推进。
- 后续接入 Sentry、Linear、Twitter、RSS、客户反馈都可以沿用同一套抽象。

### 3. Agent 并发工作会话增强

并发能力不是创建更多长期 Agent，而是让一个 Agent Worker 管理多个工作会话。

```text
plugin-dev
  ├─ 主会话：判断优先级、协调、汇报、收口
  ├─ 工作会话：Monday 插件接入
  ├─ 工作会话：Dropbox 插件接入
  └─ 工作会话：Salesforce 插件接入
```

这些工作会话：

- 继承主 Agent 的模型、权限、工具和项目 membership。
- 可以绑定具体 task / workflow step。
- 可以单独运行、失败、阻塞、完成。
- 不会出现在智能体列表里，不会变成新的长期身份。
- 由主 Agent 在 wakeup 中管理和收口。

为什么这样设计：

- 如果直接创建 `plugin-dev-1`、`plugin-dev-2`，用户会不知道谁负责。
- 如果只靠一个主 session 串行，无法处理高吞吐任务。
- 如果完全依赖 Claude Code / Codex 的原生子 Agent，会缺少平台层审计、任务绑定和流程状态。

因此 Multigent 提供统一的 `mga session` 能力，让 Agent 自主创建和管理工作会话。底层 runtime 支持 fork 就用原生 fork，不支持就降级为 fresh session + 注入上下文。

收益：

- 一个 Agent 可以同时推进多件类似工作。
- 主 Agent 仍然负责最终质量和对人沟通。
- 每个并发事项都有可追踪的 session、task、产物和审计。
- 适合插件接入、PR review、批量 issue 分流、批量测试等真实场景。

### 4. 全局上下文记忆底座

上下文中心不是知识库，也不是 Attention Signal。它是更底层的信息环境。

```text
外部系统 / 本地文件 / Runtime Session
  -> Collector
  -> Context Item
  -> Context Store
  -> 清洗 / 提炼 / 权限 / 检索
  -> Agent 主动读取
  -> 可选转成 Attention Signal
  -> 可选沉淀为知识库 / 记忆 / Skill
```

产品上尽量只暴露两个概念：

- 抓取器：负责把外部或本地信息抓进来。
- 上下文库：Agent 和用户可按权限搜索、读取的信息库。

不把“信息源”作为用户概念。信息源只是内部 metadata，用来记录 ContextItem 是从哪个 collector、哪个连接、哪个外部对象来的。

为什么不能只让 Agent 每次自己用工具拉：

- Agent 没醒时发生的信息需要先被接住。
- 多个 Agent 需要共享同一份事实。
- 外部系统数据会变化，需要历史快照。
- 重复拉取浪费成本，也容易得到不一致结果。
- 权限、脱敏、保留周期、审计需要平台统一治理。
- Attention 只应该引用上下文，不应该携带大段正文。

收益：

- 客户资料、群聊、会议、文档、Issue、PR、历史 session 可以逐步进入统一上下文。
- Agent 不再依赖一次性 prompt 背下全部世界。
- 不同 Agent 能在权限范围内共享组织记忆。
- 后续可以做清洗、摘要、遗忘、知识沉淀和上下文推荐。

## 这套设计为什么面向未来

### 1. 它承认 Agent 是长期协作主体

未来的 Agent 不会只是“输入 prompt、返回答案”的工具。它会像人一样：

- 有职责。
- 有工作节奏。
- 有协作渠道。
- 有长期记忆。
- 有对现实世界的注意力。
- 能与多人、多 Agent、多系统长期协作。

Multigent 2.x 的 Agent Worker 抽象正是为了这个方向服务。

### 2. 它把自动化从“流程触发”升级为“主体协作”

传统自动化工具的核心是：

```text
事件 -> 条件 -> 动作
```

Multigent 的方向是：

```text
世界变化 -> Attention / Context -> Agent 判断 -> 协作行动 -> 结果沉淀
```

区别在于：中间有一个具备判断力的协作主体，而不是固定脚本。

这会更适合真实工作，因为真实工作不是固定流程，而是不断判断、沟通、澄清、试错和收口。

### 3. 它允许流程保持弱约束

流程仍然重要，但流程不应该把 Agent 变成函数。

流程提供：

- 阶段边界。
- 人类审核点。
- 输出规范。
- 责任交接。
- 质量控制。

Agent 仍然可以：

- 在某个节点多次 wakeup。
- 与人类或其他 Agent 沟通。
- 阻塞时请求帮助。
- 判断准备好了再推进到下一节点。
- 必要时打回、分叉或创建工作会话。

这比 n8n 式固定自动化更适合研发、运营、客户交付这类长周期协作。

### 4. 它为企业落地留下了治理空间

企业客户真正关心的不只是“Agent 能不能干活”，还包括：

- 谁让 Agent 做了什么。
- Agent 能访问哪些数据。
- 哪些外部工具凭证被谁使用。
- 哪些信息可以进上下文库。
- 哪些动作需要人类审批。
- 多个 Agent 并发工作时如何审计和回滚。

Agent Worker、Attention Signal、Fork Session、Context Center 这几个抽象组合起来，给这些治理能力留下了清晰位置。

## 对客户和团队的实际收益

### 对管理者

- 能看到组织里有哪些 Agent，分别负责什么。
- 能看到哪些 Agent 正在运行、阻塞、等待人类判断。
- 可以通过 Lark / Feishu 像找同事一样找 Agent。
- 可以把重复流程交给 Agent 自主推进，只在关键节点介入。

### 对人类成员

- 不需要一直盯系统。
- Agent 会在需要确认时主动找人。
- 可以在 IM 里直接补充上下文、提出反馈、参与评审。
- 人类可以从“推动者”变成“审批者、教练、方向把关者”。

### 对 Agent

- 拥有长期身份和行为准则。
- 拥有项目 membership 和项目上下文。
- 能看到注意力信号，而不是被动响应单个事件。
- 能通过工作会话并发处理多个事项。
- 能从上下文库检索历史和组织记忆。

### 对组织知识

- 群聊、会议、文档、PR、Issue、历史 session 不再散落。
- 重要信息可以被沉淀成知识库文档、handoff、task receipt、skill。
- 后续新人或新 Agent 可以更快 onboarding。

## 落地方式

### 第一阶段：把 Agent 组织搭清楚

需要先回答：

- 这个 workspace 里有哪些团队：产品、工程、QA、SRE、运营、商业等。
- 每个团队有哪些角色。
- 哪些 Agent 是长期成员。
- 每个 Agent 的职责、边界、升级规则是什么。
- 每个 Agent 要加入哪些项目，以什么身份加入。

建议输出：

- 团队/角色清单。
- Agent Worker 清单。
- Agent profile / system prompt。
- Project membership 配置。
- 关键人类负责人和 IM 绑定关系。

### 第二阶段：把协作渠道跑通

重点不是让 Agent 自动回复所有消息，而是让它像同事一样能参与协作。

需要配置：

- Lark / Feishu / Slack 等 Agent 级协作渠道。
- 用户身份绑定或邮箱自动识别。
- 群聊绑定。
- Agent 对消息的心跳策略：私聊、@、卡片点击是否唤醒。
- 消息防抖和系统收到的快捷反馈。

验收标准：

- 用户能私聊 Agent。
- 群聊 @Agent 后，Agent 能在合适时间处理。
- Agent 能识别是谁找它。
- Agent 能回复到正确单聊或群聊。
- Agent 能主动找责任人确认问题。

### 第三阶段：把任务和流程弱规范化

不要一开始追求复杂流程。先把最常见的协作闭环跑通：

- 需求/问题分流。
- 技术调研和方案。
- 开发。
- 自测。
- 人工验证。
- QA。
- 发布/上线后验证。

流程节点的 prompt 要强调：

- 节点目标是什么。
- 期望输出是什么。
- 什么情况下可以继续推进。
- 什么情况下需要沟通、等待或多次 wakeup。
- 不要求 Agent 本次 run 一定完成节点。

验收标准：

- Agent 知道当前任务和流程阶段。
- Agent 能在阻塞时找人。
- Agent 能在准备好时推进流程。
- 人类节点收到的是结构化、可决策的信息。
- 任务不会因为流程变更影响正在运行的实例。

### 第四阶段：启用并发工作会话

适合先在这些场景试：

- 多个插件接入。
- 多个独立 Bug 修复。
- 多个 PR review。
- 批量 Issue triage。

落地原则：

- 主 Agent 负责拆分、分派、检查和收口。
- 工作会话负责具体单项执行。
- 每个工作会话绑定 task / project / purpose。
- 平台记录运行、状态、产物和审计。

验收标准：

- 主 Agent 能创建工作会话。
- 工作会话能独立运行并回写状态。
- 主 Agent 能知道哪些工作会话完成、失败或阻塞。
- 用户能在运行页面看到并发情况。

### 第五阶段：建设上下文库

第一批上下文建议从高价值、低歧义的信息开始：

- 项目设计文档。
- 关键会议纪要。
- 历史 Agent session。
- PR review 总结。
- Issue / 用户反馈。
- 操作文档和 debug runbook。

Collector 的落地方式：

- 官方本地 collector：手动文本、本地文件、本地 Agent session。
- 客户侧 collector：飞书/Lark、GitHub、Linear、Sentry 等，可以独立进程写入。
- SaaS 未来可以提供 collector marketplace。

验收标准：

- 用户可以把资料写入上下文库。
- Agent 可以通过 `mga context` 搜索和读取。
- 权限边界清晰。
- 重要上下文可以关联到 Agent 或项目。

## 展示时可以用的讲法

### 讲法一：从工具到同事

过去的软件自动化是“我配置一个流程，它按规则执行”。

Multigent 的目标是“我雇佣一批 Agent 同事，他们有职责、有上下文、有工作节奏，会自己判断、沟通、推进和沉淀”。

### 讲法二：流程不是 n8n

Multigent 的流程不是固定代码流，而是协作规范。就像公司里开发流程不是为了限制人，而是为了让人和 Agent 都知道什么时候该调研、什么时候该评审、什么时候该测试、什么时候该找负责人确认。

### 讲法三：Attention 是 Agent 的收件箱和现实感知

人不是每秒钟响应世界上的所有事件。人会看消息、看任务、看告警、判断优先级。Agent 也应该如此。Attention Signal 就是给 Agent 的现实感知入口。

### 讲法四：上下文库是组织记忆，不是 prompt 堆料

我们不把所有资料塞进 prompt。我们把资料放进上下文库，让 Agent 像人查资料一样按权限检索。这样才能长期运转、可审计、可遗忘、可复用。

## 当前仍需继续打磨的问题

### 1. IM 多用户协作体验

已经支持私聊、群聊、绑定身份、卡片交互和防抖唤醒，但还要继续测试：

- 多用户同时找同一个 Agent。
- 多个 Agent 在同一个群里协作。
- Agent 是否能自然识别责任人和权限。
- 卡片、Markdown、文件、图片、云文档的体验。

### 2. 权限模型细化

需要继续完善：

- 人管理 Agent 的权限。
- Agent 访问项目、工具、上下文的权限。
- IM 用户身份和 Multigent 用户身份的绑定。
- Agent 代表用户操作流程时的委托和审计。
- ContextItem 的敏感度和 ACL。

### 3. Collector 生态

第一版官方入口已经支持手动文本、本地文件、本地 session。下一步要做：

- Lark / Feishu Collector。
- GitHub Collector。
- Linear / Sentry Collector。
- 客户侧 collector daemon。
- Collector marketplace。

### 4. Agent 表现调试方法

技术能力具备后，还需要形成一套调试 Agent 表现的方法：

- 场景设计。
- 团队/角色/项目 prompt。
- Agent profile。
- Wakeup routine。
- 流程输入输出规范。
- 多用户、多 Agent、多轮协作测试。
- 失败归因：是代码问题、权限问题、prompt 问题，还是流程设计问题。

## 总结

Multigent 2.x 这轮改动的本质，是在为“Agentic Company”打地基。

它不是简单把 Agent 从项目页面搬到一级页面，也不是简单加一个消息队列或上下文库。真正的变化是：

- Agent 拥有长期身份。
- 项目成为 Agent 工作的上下文，而不是 Agent 的本体。
- Attention 让 Agent 具备现实感知。
- Fork Session 让 Agent 具备并发工作能力。
- Context Center 让组织记忆可采集、可检索、可治理。
- Workflow 继续作为人和 Agent 的弱协作规范。
